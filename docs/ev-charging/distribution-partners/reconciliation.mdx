# Reconciliation

Completed sessions are the primary artefact you reconcile against. Each
completed session includes `total_cost` — the final amount for the charging
session.

## Pull completed sessions

Poll completed sessions to reconcile against your books. Use `updated_since`
to fetch only records that changed since your last check.

```http
GET /dp/v1/sessions?status=COMPLETED&updated_since=2026-04-29T00:00:00Z&limit=100
Authorization: Bearer <your_dp_api_key>
X-Request-ID: c0a3d9e5-8094-4d6f-d1a2-6d1f4a7f8f95
```

**Response** — `HTTP 200`:

```json
{
  "data": [
    {
      "id":               "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
      "reference":        "your-order-123",
      "status":           "COMPLETED",
      "location_id":      "LOC001",
      "charge_point_id":  "LOC001-CP-1",
      "connector_id":     "1",
      "start_time":       "2026-04-29T10:15:00Z",
      "end_time":         "2026-04-29T11:00:00Z",
      "kwh":              25.0,
      "currency":         "MXN",
      "total_cost":       188.50,
      "created_at":       "2026-04-29T10:14:50Z",
      "updated_at":       "2026-04-29T11:00:01Z"
    }
  ],
  "total_count": 1,
  "limit": 100,
  "offset": 0
}
```

:::info No separate CDR pull needed
The session object includes `total_cost` once the session reaches `COMPLETED`
status. There is no separate CDR endpoint — the hub resolves charge detail
records internally and surfaces the final cost directly on the session.
:::

## Recommended reconciliation pattern

1. **Real-time**: subscribe to the [`session.settled` webhook](/webhooks/events) — every settled session POSTs the cleared amounts to you the moment they're finalised
2. **Daily batch**: pull `GET /dp/v1/sessions?status=COMPLETED&updated_since=<24h ago>` and reconcile against your books — catches any webhook deliveries that failed
3. **Weekly safety net**: pull `GET /dp/v1/sessions?status=COMPLETED&updated_since=<7 days ago>`, compare counts against your local store. Any drift triggers a re-import of just the missing IDs
