# Interoperability statement

NetworkCore Hub implements **OCPI 2.2.1** as a roaming hub. This page lists,
module by module, what we implement and what we don't — so an integration
engineer at AMPECO, EVOS, Monta, Wallbox, ChargePoint or a custom CSMS can
audit conformance up front and not discover surprises mid-integration.

## OCPI version support

| Version | Status | Notes |
|---|---|---|
| **2.2.1** | ✅ Supported | The canonical version. All modules below refer to 2.2.1 unless noted. |
| 2.3 | 🛣️ Roadmap | Additive when stable; will appear in `/ocpi/versions` alongside 2.2.1, never replacing. |
| 2.2 | ❌ Not supported | Use 2.2.1 (the differences are minor and we maintain only one version). |
| 2.1.1 | ❌ Not supported | Older partners must upgrade. |
| 2.0 / 2.1 | ❌ Not supported | |

## Roles

NetworkCore operates as a **Hub** between CPOs (charge-point operators) and
eMSPs (the OCPI name for what we commercially call Distribution Partners /
DPs). Private Hosts integrate as CPOs.

| Role | We act as | Notes |
|---|---|---|
| Hub | ✅ Yes | Receive + forward between CPOs and eMSPs |
| CPO | ❌ No | We do not operate chargers ourselves |
| eMSP | ❌ No | We do not operate driver apps ourselves |
| NSP / NAP / SCSP / Other | ❌ No | Out of scope for the current commercial model |

## Modules

Every cell below is the contract. If we say ✅ on Receiver, you can `PUT`
to that endpoint. If we say ❌ on Sender, don't expect `GET` to be useful.

| Module | Hub as Receiver (you PUT/POST) | Hub as Sender (you GET) | Notes |
|---|---|---|---|
| **Credentials** | ✅ POST + PUT + GET + DELETE | — | The handshake module. Required first. |
| **Locations** | ✅ `cpo/locations/{cc}/{pid}/{location_id}` (CPO PUTs) | ✅ `emsp/locations` (eMSP GETs) | EVSE-granular updates supported. |
| **Tariffs** | ✅ `cpo/tariffs/{cc}/{pid}/{tariff_id}` (CPO PUTs) | ✅ `emsp/tariffs` (eMSP GETs) | Element-level pricing rules with restrictions. |
| **Sessions** | ✅ `cpo/sessions/{cc}/{pid}/{session_id}` (CPO PUTs) | ✅ `emsp/sessions` (eMSP GETs) | Partial updates allowed. ChargingPreferences not yet supported. |
| **CDRs** | ✅ `cpo/cdrs` (CPO POSTs) | ✅ `emsp/cdrs` (eMSP GETs) | Idempotent via `(cc, pid, id)`. CDR mutation after POST not supported (CDR is immutable). |
| **Tokens** | ✅ `emsp/tokens/{cc}/{pid}/{token_uid}` (eMSP PUTs) | ✅ `cpo/tokens` (CPO GETs) | Authorize-able tokens are surfaced to CPOs; PIN auth not supported. |
| **Token Authorize** | ✅ `cpo/tokens/{cc}/{pid}/{token_uid}/authorize` | — | Real-time auth supported; we hold token state for caching. |
| **Commands** | ✅ `cpo/commands/{type}` (eMSP triggers) | ✅ Callback URL on `commands` response | START_SESSION + STOP_SESSION + RESERVE_NOW + UNLOCK_CONNECTOR + CANCEL_RESERVATION |
| **ChargingProfiles** | ❌ Not implemented | ❌ Not implemented | Roadmap — smart-charging integration is post-MVP. |
| **HubClientInfo** | 🟡 Best-effort | 🟡 Best-effort | We track party online status for ops visibility but don't proactively publish HubClientInfo updates. |

## Status codes we return

Standard OCPI status codes per the spec:

| Code | Meaning | When you'll see it |
|---|---|---|
| 1000 | Success | Happy path. |
| 2000 | Generic client error | Unused — we always return a more specific code. |
| 2001 | Invalid or missing parameters | Required field missing, wrong type, bad enum value. |
| 2002 | Not enough information | The shape was valid but the payload doesn't carry enough data to act on. |
| 2003 | Unknown location | CDR references a `location_id` the hub doesn't know — push the Location first. |
| 2004 | Unknown token | CDR or session references a token UID we've never seen — eMSP must PUT it first. |
| 3000 | Generic server error | A 5xx on our side. Includes a message hint; if you see this in production please file a partner@networkcore.org ticket with the X-Request-ID. |
| 3001 | Unable to use the client's API | Hub callback to your endpoint failed. Comes with a classification: `dns_unresolved` / `refused` / `timeout` / `tls` / `auth_rejected` / `http_error`. |
| 3002 | Unsupported version | You requested a version other than 2.2.1. |
| 3003 | No matching endpoints | We couldn't find the module in your endpoints list. |

## Authentication

OCPI 2.2.1 base64-encodes the Token in the `Authorization: Token <base64>`
header. We accept both the raw token and the base64 form on incoming
requests, but always emit the base64 form on outgoing calls.

- **Token A:** pre-shared, used only for the initial credentials POST.
  Issued by NetworkCore via the partner portal.
- **Token C:** generated by NetworkCore during the handshake, used for all
  subsequent calls in both directions.
- **Rotation:** partners can self-rotate Token A from the portal
  Integration tab; Token C rotation requires a fresh credentials POST.

## Rate limits

| Tier | Rate | Applies to |
|---|---|---|
| OCPI write | 60 req/s burst, 1000 req/min sustained, per Token C | CDR posts, session updates, location pushes |
| OCPI read | 200 req/s burst, 5000 req/min sustained, per Token C | Sessions, CDRs, locations pulls by eMSP |
| Admin | 30 req/s burst, 500 req/min, per admin JWT | The admin console |

Exceeded limits return HTTP 429 with a `Retry-After` header. Sustained
abuse triggers a temporary block and an alert to ops.

## Webhooks (NetworkCore → partner)

These are NetworkCore extensions, not OCPI. Available events:

| Event | Triggered when |
|---|---|
| `session.settled` | A session's CDR has been validated, cleared, and the per-party amounts have landed in the wallet. |
| `settlement.batch_completed` | A SPEI/SEPA/ACH payout to the partner has cleared. |
| `chargeback.opened` | A dispute has been opened against a session involving the partner. |
| `chargeback.evidence_submitted` | We've submitted the evidence pack to the PSP. |
| `chargeback.resolved` | The PSP has returned a final verdict (won / lost). |

Each delivery carries `X-NetworkCore-Signature: sha256=<hex>` computed
over the body with the secret you provided when registering the endpoint.
Verify the signature before acting on the payload.

## Extensions

| Extension | Status | Notes |
|---|---|---|
| Risk fingerprints | ✅ Live | `device_hash` / `account_hash` / `vehicle_hash` posted alongside session data. Network-wide fraud correlation. See [Risk fingerprints](/ev-charging/distribution-partners/risk-fingerprints). |
| 3DS recommendation | ✅ Live | We score each session and recommend whether the PSP should challenge with 3DS. |
| First-loss envelope | ✅ Live | NetworkCore absorbs a per-currency cap of chargeback losses before any partner deduction. |
| Tiered reserves | ✅ Live | Per-CPO rolling reserve, configurable %. |
| Driver API | ✅ Live | App-facing REST API. Distinct from OCPI eMSP; used by DPs who don't want to implement OCPI client themselves. |

## What we explicitly DO NOT do

These come up regularly in partner discussions. Saying no up front saves
everyone time.

- **No OCPP**. The hub is OCPI-only. If your chargers speak OCPP, they need
  to go through a CSMS (AMPECO, EVOS, Wallbox Bond, Monta, etc.) that
  speaks OCPI to us.
- **No charger firmware**. We don't sign firmware, manage rollouts, or
  diagnose charger hardware.
- **No driver KYC**. The DP/eMSP holds driver identity; we hold a
  `driver_hash` for risk correlation only.
- **No card-network direct integration**. Money moves via PSPs (Parco, etc.)
  for card acquiring, and via banking rails (SPEI, SEPA, ACH) for payouts.

## Versioning policy

OCPI surface changes follow the OCPI working group's cadence (we ship the
spec version when it's stable, never before). NetworkCore extensions
(webhooks, fingerprints, Driver API) follow semantic versioning with a
6-month deprecation window for breaking changes — announced via the
[changelog](/changelog) and the partner portal banner.
